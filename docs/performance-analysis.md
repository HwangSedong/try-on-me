# 성능 분석: 결과 이미지 저장소 개선 전후

## 1. 목적

결과 이미지와 의류 컷아웃을 무제한으로 메모리에 보관하던 구조가 운영 메모리 한도(`MemoryMax=384M`) 안에서 실제로 문제를 일으키는지 확인했습니다. 그리고 상한이 있는 저장소로 바꾼 뒤 같은 조건에서 다시 측정했습니다.

> 이 측정은 **백엔드 처리와 저장 구조**의 측정입니다. 이미지 생성 모델(OpenAI)의 품질이나 지연은 포함하지 않았습니다. 실제 OpenAI API는 호출하지 않았습니다.

## 2. 테스트 환경

| 항목 | 값 |
|---|---|
| 실행 모드 | `--mode local`: 같은 PC에서 서버를 별도 프로세스로 실행 |
| OS / CPU / RAM | Windows 11 (10.0.26200), Intel Core Ultra 7 258V (논리 8코어), 31.6 GB |
| Python / FastAPI / uvicorn | 3.13.14 / 0.162.0 / 0.54.0 (서버와 클라이언트 동일) |
| 서버 실행 | `uvicorn`, worker 1개, 접근 로그 끔, 서버 stdout은 `DEVNULL` |
| 메모리 한도 | **강제하지 않음.** 운영 한도 384 MiB와 RSS를 비교만 함 |
| 변경 전 코드 | 커밋 `119bfff`의 `backend/`(`git archive`로 추출) |
| 변경 후 코드 | 이 작업 트리의 `backend/` |

운영과 같은 384 MiB 한도를 cgroup으로 강제하는 Docker 모드(`--memory 384m --cpus 0.4`, Python 3.10)도 만들었습니다. 그러나 작업 PC의 Docker Desktop(Inference manager 초기화 오류)과 Podman VM(디스크 파일 없음)이 모두 기동에 실패해서 실행하지 못했습니다. **따라서 "OOM으로 프로세스가 종료됐다"는 결과는 관측하지 않았습니다.** 아래 결과는 RSS가 한도를 넘는다는 측정까지만 보여줍니다.

## 3. 측정 방법

- `benchmarks/bench_server.py`가 측정 대상 버전의 실제 앱을 불러옵니다. 이미지 생성 Provider와 의류 준비기만 고정 크기 바이트를 돌려주는 가짜로 바꿉니다. 결과는 2 MiB, 컷아웃은 1.5 MiB이고, 근거는 `benchmarks/README.md`에 있습니다.
- 1회 반복은 `POST /api/garments/prepare → GET cutout → POST /api/generate → GET result`입니다.
- 순서는 순차 100회(10, 50, 100회 시점 스냅숏) → 3초 유휴 → 동시성 8로 100회 추가입니다.
- RSS는 서버 프로세스의 Working Set이고, Peak는 `peak_wset`입니다. 저장 이미지 수와 바이트는 서버 안에서 직접 셉니다.
- 버전마다 서버를 새로 띄워 **3회 반복**했습니다. 표의 값은 반복 3회의 평균 ± 표본 표준편차입니다. 응답시간 P95는 반복마다 계산한 뒤 평균을 냈습니다.
- 버전별로 순차 1,200건, 동시 1,200건 요청을 보냈습니다. 원본 데이터는 `benchmarks/results/*.csv`, `*.json`에 있습니다.
- 세 조건:
  - `baseline`: 변경 전
  - `after`: 변경 후, `LOG_LEVEL=INFO`. 로그를 실제로 출력합니다.
  - `after-log-warning`: 변경 후, INFO 로그 끔. 변경 전 코드는 로거 핸들러가 없어 로그를 출력하지 않았으므로, 응답시간은 이 조건과 비교해야 공정합니다.

## 5. 해석

### 문제 재현

- 변경 전에는 요청 1회(결과 + 컷아웃)마다 RSS가 약 **3.6 MiB씩 선형으로** 늘었습니다. 50회와 100회 측정 사이 기울기가 3.57 MiB/회입니다. 저장 바이트(3.5 MiB/회)와 거의 일치합니다. 3초 유휴 뒤에도 RSS는 줄지 않았습니다(440.4 → 437.7 MiB). 요청 처리 중의 일시 메모리가 아니라, **보관된 데이터 자체**가 메모리를 차지하고 있다는 뜻입니다.
- 100회 시점 RSS 440 MiB는 운영의 `MemoryMax=384M`보다 큽니다. 두 측정점 사이를 선형 보간하면 약 61회에 `MemoryHigh=300M`, 약 84회에 `MemoryMax=384M`을 넘습니다. 이 값은 **추정치**입니다. 측정점은 10, 50, 100회뿐이고, 한도를 실제로 강제하지 않았습니다.
- 반복 3회의 편차가 0.5 MiB 이내라서 재현성이 높습니다.

### 개선 효과

- 변경 후에는 50회 이후 RSS가 **약 145~155 MiB에서 더 늘지 않았습니다.** 기본 RSS 약 80 MiB에 저장소 예산 64 MiB, 그리고 약 10 MiB가 더해진 값입니다. 요청을 100회에서 200회로 두 배 늘려도 RSS는 6.4 MiB만 늘었습니다. 변경 전에는 353 MiB가 늘었습니다.
- Peak RSS 160.5 MiB는 `MemoryHigh=300M`보다 약 140 MiB 낮습니다. 이 여유는 실제 OpenAI 응답 디코딩과 원본 해상도 리사이즈 같은 일시 메모리에 쓰입니다.
- **저장 바이트 감소와 RSS 감소는 구분해야 합니다.** 저장 바이트는 정책 그대로 64 MiB 이하에 묶였습니다. 이것은 저장소가 보장하는 값입니다. RSS도 같이 묶였지만, 이번 측정은 Windows 힙에서 했습니다. 큰 블록을 해제하면 OS에 바로 돌려주는 환경입니다. Linux glibc malloc은 해제된 메모리를 힙에 남겨둘 수 있어서, 운영 환경 RSS는 이보다 높게 머물 수 있습니다. Docker 모드로 Linux에서 다시 측정하기 전까지는 운영 RSS 수치를 단정하지 않습니다.

### 응답시간

- 순차 요청의 응답시간, 처리량, 오류율은 반복 간 편차 안에서 같았습니다. 저장소의 잠금과 LRU 관리(최대 100항목 순회) 비용은 측정에서 드러나지 않았습니다.
- 동시성 8에서 `after`의 `POST /api/generate` P95가 약 19 ms(+12.8%) 높았습니다. 같은 코드에서 INFO 로그만 끈 `after-log-warning`은 변경 전과 같았습니다(150.96 vs 149.59 ms). 그래서 차이의 원인은 저장소가 아니라 **이번에 고친 로그 출력(포맷팅과 stdout 쓰기)**으로 봅니다. 다만 차이가 반복 간 표준편차(9~13 ms)의 약 1.5배라서, 3회 반복으로는 확정하기 어렵습니다. 실제 이미지 생성은 수십 초가 걸리므로 운영 체감에는 영향이 없을 것으로 판단했고, 관측성을 유지하기로 했습니다.
- `GET /api/results/{id}`가 약 110 ms(P95)인 것은 2 MiB 응답 본문을 루프백으로 전송하는 비용입니다. 두 버전이 같습니다.

## 6. 트레이드오프

| 얻은 것 | 잃은 것 |
|---|---|
| 요청 수와 무관하게 상한이 있는 메모리 사용 | 30분 지난 결과는 404 |
| 프로세스 전체 OOM 대신 결과 1건 404라는 국소적인 실패 | 동시 사용자가 많으면 아직 보고 있는 결과가 LRU로 밀려날 수 있음 (64 MiB ≈ 결과 30장) |
| 저장소 상태(개수, 바이트, 축출, 만료)가 로그로 보임 | INFO 로그 출력 비용 (동시 P95 +19 ms 관측, 확정 아님) |

## 7. 남은 한계

1. **OOM 종료 자체는 재현하지 않았습니다.** cgroup 한도를 강제하는 Docker 모드를 실행하지 못했습니다.
2. 측정은 Windows와 Python 3.13에서 했습니다. 운영은 Linux와 Python 3.10입니다. RSS의 절대값과 해제 동작은 다를 수 있습니다. 저장 바이트 수치는 플랫폼과 무관합니다.
3. 가짜 Provider는 바이트 크기만 재현합니다. 실제 OpenAI 경로의 base64 디코딩, PIL 리사이즈 같은 일시 메모리는 측정하지 않았습니다. 그래서 64 MiB 예산의 여유분은 추정입니다.
4. CPU 제한(`CPUQuota=40%`)을 적용하지 않았습니다. 처리량의 절대값은 운영과 다릅니다. 이번 비교에서는 두 버전 사이의 상대 비교로만 씁니다.
5. 반복 3회는 작은 지연 차이를 판정하기에 부족합니다.
