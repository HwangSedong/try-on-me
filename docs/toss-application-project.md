# Try-On-Me: 단일 프로세스 이미지 서버의 무제한 보관 문제를 측정하고 해결한 과정

> 이 문서의 모든 수치는 `benchmarks/results/`의 원본 데이터와 `docs/performance-analysis.md`에서 나왔습니다. 측정하지 않은 항목은 측정하지 않았다고 적었습니다.

## 1. 프로젝트 개요와 역할

- **Try-On-Me**는 전신 사진 1장과 의류 참조 이미지(상의·하의·아우터·신발·모자·액세서리)를 받아, 인물을 유지한 채 옷만 바꾼 이미지를 생성하는 가상 피팅 서비스입니다.
- 2023년 Angular와 VITON-HD로 만든 대학 프로젝트를 **2026년 10월 초 React + FastAPI + OpenAI Images Edit API 구조로 다시 만들었습니다.** 개발부터 GitHub Actions → Lightsail(systemd + Nginx) 배포까지 혼자 맡고 있습니다.
- 이 문서는 그 리빌드 이후 **2026-10-26 하루 동안 진행한 서버 안정성 개선 작업**을 다룹니다. 리빌드 자체(Provider 추상화, 파이프라인, 배포 구조)는 이 작업 전에 이미 있었습니다.

## 2. 가장 어려웠던 문제

**"아직 장애가 나지 않은" 메모리 문제를 장애 전에 증명하고, 운영 제약(단일 worker, 384 MiB) 안에서 해결하는 일**이었습니다.

생성 결과와 의류 컷아웃 이미지가 모듈 전역 딕셔너리에 영구 보관되고 있었습니다. 코드만 봐서는 "언젠가 문제가 될 수 있다"는 추측에 그칩니다. 실제로 몇 번의 요청에서 한도에 닿는지, 고친 뒤 메모리가 정말 평평해지는지는 측정해야 알 수 있었습니다. 하지만 기존 Mock Provider는 업로드한 이미지를 그대로 돌려주기 때문에, 그대로 부하를 주면 문제가 드러나지 않았습니다.

## 3. 문제를 발견한 배경

배포 설정(`deploy/try-on-me.service`)에는 `--workers 1`, `MemoryHigh=300M`, `MemoryMax=384M`이 걸려 있습니다. 같은 인스턴스를 다른 서비스와 나눠 쓰기 때문입니다. 반면 `api/generation.py`는 결과와 컷아웃을 이렇게 보관하고 있었습니다.

```python
_results: dict[str, ImageAsset] = {}
_cutouts: dict[str, ImageAsset] = {}
```

삭제하는 코드가 어디에도 없었습니다. 실제 생성 결과 PNG(1086×1448)는 1.6~2.0 MB입니다. 한도와 견주면 결과를 백여 장만 쌓아도 한도에 닿는 구조였습니다.

## 4. 기존 아키텍처의 한계

- **무제한 보관:** 만료, 개수, 바이트 상한이 하나도 없었습니다.
- **실패 범위가 넓음:** 한도를 넘으면 cgroup이 프로세스를 종료합니다. 그 순간 진행 중인 생성 요청과 그때까지의 모든 결과가 함께 사라집니다.
- **관측 불가:** 몇 장이 몇 바이트를 차지하는지 알 방법이 없었습니다. 측정 중에 추가로 발견한 것도 있습니다. `request_id` 단계 로그를 남기는 로거에 출력 핸들러가 없어서, uvicorn으로 실행하면 INFO 로그가 **전혀 출력되지 않았습니다.** 테스트는 pytest `caplog`가 루트 로거에 핸들러를 붙이기 때문에 통과하고 있었습니다.

## 5. 원인 분석 과정

1. **메모리 누수인지, 무제한 보관인지 구분했습니다.** 객체는 딕셔너리에서 정상적으로 참조되고 있었습니다. 그래서 GC로 회수되는 대상이 아니고, 보관 정책이 없는 것이 원인이라고 가설을 세웠습니다.
2. **재현 가능한 부하 도구를 만들었습니다.** 변경 전 코드(`119bfff`)와 변경 후 코드를 같은 래퍼로 불러오고, 이미지 생성 Provider만 고정 크기(결과 2 MiB, 컷아웃 1.5 MiB)의 새 버퍼를 돌려주는 가짜로 바꿨습니다. 실제 Provider가 base64를 디코딩해 새 `bytes`를 만드는 동작과 같습니다. 업로드 검증, 파이프라인, 라우트, 저장은 측정 대상 코드를 그대로 씁니다.
3. **가설을 숫자로 확인했습니다.** 변경 전에는 요청 1회마다 RSS가 3.57 MiB씩 선형으로 늘었습니다. 저장 바이트 증가량 3.5 MiB/회와 일치했습니다. 3초 쉬어도 줄지 않았습니다(440.4 → 437.7 MiB). 반복 3회의 편차는 0.5 MiB 이내였습니다. 100회 시점 RSS 440 MiB는 운영 한도 384 MiB를 넘습니다.

## 6. 비교한 대안

| 대안 | 기각·보류 이유 |
|---|---|
| 주기적 재시작 | 재시작 순간 진행 중인 요청과 결과가 사라짐. 원인을 그대로 둠 |
| TTL만 적용 | 짧은 시간에 요청이 몰리면 TTL 전에 한도를 넘음 |
| 개수 상한만 적용 | 이미지 크기가 해상도에 따라 수십 배 달라서 바이트를 통제하지 못함 |
| 로컬 디스크 | 정리 작업, 용량, 릴리스 디렉터리를 심볼릭 링크로 교체하는 배포 구조와 경로가 얽힘 |
| Redis | 같은 인스턴스의 메모리를 나눠 쓰므로 문제가 다른 프로세스로 옮겨갈 뿐 |
| S3 + 서명 URL | 영속성은 생기지만, 계정도 보관 기능도 없는 서비스에 비용과 개인정보 관리 부담이 큼 |

## 7. 최종 선택

**TTL + 개수 상한 + 바이트 상한 + LRU 축출을 갖춘 인메모리 `TemporaryImageStore`**를 선택했습니다.

- 결과와 컷아웃이 **하나의 바이트 예산(64 MiB)을 합산해서** 씁니다. 둘이 같은 프로세스 메모리를 두고 경쟁하기 때문입니다.
- 예산 근거: 기본 RSS 약 80 MiB와 요청 처리 중 일시 메모리(업로드, base64 응답, PIL 리사이즈 버퍼)의 여유를 남기고 `MemoryHigh=300M` 아래에 머물도록 잡았습니다. 일시 메모리는 실측하지 않은 추정이라는 점을 문서에 남겼습니다.
- 목표는 실패 모드를 **"프로세스 전체 OOM 종료"에서 "오래된 결과 1건 404"로** 바꾸는 것이었습니다. 이 서비스는 프론트엔드가 응답 직후 결과를 가져가기 때문에, 이 교환이 합리적이라고 판단했습니다.
- 다중 worker, 결과 보관 기능, 결과 조회 404 증가가 나타나면 객체 저장소로 옮겨야 합니다. 이 조건을 ADR에 명시했습니다.

## 8. 구현 내용

- `backend/app/services/temporary_image_store.py`
  - `put(kind, image)`: 만료 항목 정리 → 상한을 넘으면 LRU 순으로 축출 → 저장. 예산보다 큰 이미지는 **기존 항목을 하나도 지우지 않고** `ImageTooLargeToStoreError`로 거부합니다.
  - `get(kind, id)`: 만료를 검사하고 LRU 순서를 갱신합니다. 컷아웃 ID로 결과를 조회할 수 없게 종류(kind)를 구분합니다.
  - `time.monotonic()` 기준 TTL이며 시계 함수를 주입할 수 있습니다. `threading.Lock`으로 정합성을 지키고, 저장·축출·만료·거부 통계를 남깁니다.
- `backend/app/api/generation.py`: 전역 딕셔너리를 없애고 `app.state.image_store`를 주입받습니다. 저장 불가 시 `507`을 반환합니다. **응답 스키마와 URL 형식은 그대로라서 프론트엔드 변경이 없습니다.**
- 관측성:
  - 로거에 stdout 핸들러를 추가했습니다(로그가 안 나오던 문제 수정).
  - 완료 로그에 단계별 시간(`upload`, `preprocessing`, `generation`, `safety`, `quality`, `store`), 출력 크기, 저장소 사용량, 축출·만료 수를 남깁니다.
  - 파일명, 프롬프트, 이미지 바이트는 남기지 않습니다(테스트로 확인).
- CI: 배포 워크플로에 Python 3.10 오프라인 테스트 job을 추가하고, 배포가 테스트 통과에 의존하도록 했습니다(`needs: test`). 아직 GitHub에 push하지 않아 Actions에서는 실행되지 않았습니다.

## 9. 성능 평가와 검증 결과

**측정 조건:** 같은 PC(Windows 11, Python 3.13)에서 서버를 새로 띄워 버전마다 3회 반복했습니다. 1회 반복은 컷아웃 준비 → 조회 → 생성 → 조회이고, 순차 100회 뒤 동시성 8로 100회를 추가했습니다. 버전마다 2,400건씩 요청했습니다.

| Metric | 변경 전 | 변경 후 | 변화 |
|---|---|---|---|
| 100회 후 RSS | 440.4 MiB | 147.8 MiB | -66.4% |
| 누적 200회 후 RSS | 793.7 MiB | 154.2 MiB | -80.6% |
| Peak RSS | 793.7 MiB | 160.5 MiB | -79.8% |
| 200회 후 저장 바이트 | 700.0 MiB | 64.0 MiB (예산 상한) | -90.9% |
| 100회 → 200회 RSS 증가 | +353 MiB | +6.4 MiB | |
| 순차 `POST /api/generate` P95 | 4.83 ms | 4.97 ms | 편차 범위 안 |
| 동시성 8 처리량 | 41.8 req/s | 40.9 req/s | 편차 범위 안 |
| 오류율 | 0% | 0% | |

- 동시성 8의 생성 API P95는 변경 후 +19 ms(+12.8%)였습니다. 로그를 끈 같은 코드는 변경 전과 같아서(150.96 vs 149.59 ms), 차이는 새로 동작하기 시작한 로그 출력 비용으로 봅니다. 반복 3회로는 확정하기 어렵다고 함께 기록했습니다.
- 자동화 테스트는 15개에서 42개로 늘었고 모두 통과합니다.
  - 저장소: TTL 만료, LRU 순서, 바이트·개수 상한, 결과·컷아웃 합산 예산, 큰 이미지 거부 후 상태 보존, 8스레드 × 200회 동시 저장·조회 정합성
  - API: 빈 파일, 이미지가 아닌 바이트, 413, Provider 오류 502, 재시도 소진 422, 만료·축출 404, 507, 동시 생성 20건
- 프론트엔드 프로덕션 빌드가 성공했고, mock 모드에서 실제 uvicorn을 띄워 준비 → 생성 → 조회 흐름과 로그 출력을 확인했습니다.

## 10. 시행착오와 교훈

- **Mock이 문제를 숨겼습니다.** 기존 Mock은 업로드 객체를 그대로 돌려주기 때문에 저장 데이터가 업로드 크기에 묶여서, 실제 서비스 상황을 재현하지 못했습니다. 측정 대상과 같은 성질(새로 할당되는 고정 크기 응답)을 가진 가짜를 따로 만들어야 했습니다.
- **테스트가 통과해도 운영 로그는 비어 있을 수 있습니다.** `caplog`는 루트 로거에 핸들러를 붙이기 때문에, 운영 프로세스의 출력 경로를 검증하지 못합니다. 서버를 실제로 띄워 보고서야 발견했습니다.
- **"저장 바이트 감소"와 "RSS 감소"는 다른 주장입니다.** 저장 바이트는 정책이 보장하는 값입니다. RSS는 할당기가 메모리를 OS에 언제 돌려주느냐에 달려 있습니다. Windows에서 측정한 RSS를 Linux 운영 수치로 옮겨 말하지 않았습니다.
- **재현 환경을 끝까지 만들지 못했습니다.** 운영과 같은 cgroup 384 MiB 한도로 OOM 종료를 직접 보려고 Docker 모드를 만들었지만, 작업 PC의 Docker Desktop과 Podman이 기동에 실패했습니다. 그래서 "OOM이 발생했다"가 아니라 "RSS가 한도를 넘었다"까지만 주장합니다.

## 11. 남아 있는 한계

1. OOM 종료 자체는 관측하지 않았습니다. Linux와 Python 3.10 cgroup 환경 측정(`--mode docker`)이 남아 있습니다.
2. 64 MiB 예산의 근거인 "요청 처리 중 일시 메모리"는 실제 OpenAI 응답과 큰 원본 이미지로 측정하지 않았습니다.
3. 인메모리 저장소이므로 재시작하면 결과가 사라지고 worker 사이에 공유되지 않습니다.
4. 안전성·품질 검증기는 여전히 Mock입니다. 수동 평가 양식(`docs/quality-evaluation.md`)만 마련했고, 실제 평가는 하지 않았습니다.
5. CI 테스트 job은 작성했지만 아직 GitHub Actions에서 실행되지 않았습니다.
