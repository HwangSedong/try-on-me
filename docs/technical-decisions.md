# 기술 의사결정 기록 (ADR)

## ADR-1. 결과 이미지 보관: 상한이 있는 인메모리 저장소

**상태:** 채택 (2026-10-26)

### 해결하려는 문제

`api/generation.py`의 `_results`, `_cutouts` 딕셔너리는 요청마다 이미지 바이트를 추가하기만 하고 삭제하지 않았습니다. 운영 프로세스는 단일 worker이고 `MemoryMax=384M`입니다. 그래서 요청이 누적되면 cgroup 한도에 닿아 프로세스가 OOM으로 종료될 수 있습니다. 종료되면 그때까지의 모든 결과도 함께 사라집니다. 벤치마크에서는 순차 100회(결과 100장과 컷아웃 100장)만에 저장 바이트가 350 MiB에 이르렀습니다. 수치는 `performance-analysis.md`에 있습니다.

### 고려한 대안

| 대안 | 장점 | 단점 | 판단 |
|---|---|---|---|
| A. 그대로 두고 주기적으로 재시작 | 코드 변경 없음 | 재시작 순간 진행 중인 요청과 결과가 사라짐. 근본 원인을 그대로 둠 | 기각 |
| B. TTL만 적용 | 구현이 단순함 | 짧은 시간에 요청이 몰리면 TTL 전에 한도를 넘음. 메모리 상한을 보장하지 못함 | 단독으로는 기각 |
| C. 개수 상한만 적용 (LRU) | 단순하고 메모리 상한이 생김 | 이미지 크기가 입력 해상도에 따라 수십 배 달라서 개수로는 바이트를 통제하지 못함 | 단독으로는 기각 |
| **D. TTL + 개수 + 바이트 상한 + LRU (인메모리)** | 외부 의존성 없이 메모리 상한을 보장. 기존 API 그대로. 단위 테스트로 검증 가능 | 프로세스 재시작 시 사라지고 worker 사이에 공유 안 됨 | **채택** |
| E. 로컬 디스크 임시 파일 | 메모리 사용이 줄어듦 | 파일 정리, 디스크 용량, 동시성 처리가 새로 필요. 릴리스 디렉터리를 심볼릭 링크로 교체하는 배포 구조와 경로 관리가 얽힘 | 보류 |
| F. Redis | worker 간 공유, TTL 내장 | 같은 2 GB급 인스턴스에서 메모리를 나눠 쓰므로 문제가 다른 프로세스로 옮겨갈 뿐. 운영 대상이 늘어남 | 보류 |
| G. S3 등 객체 저장소 + 서명 URL | 영속성, 수평 확장 | 비용, 접근 권한, 보존 정책, 개인정보(인물 사진 결과) 관리가 새로 필요 | 다중 인스턴스나 결과 보관 기능이 생기면 재검토 |

### 선택 이유

- 이 서비스에는 계정과 결과 보관함이 없습니다. 프론트엔드는 응답을 받자마자 결과 URL을 가져옵니다. 결과에 필요한 수명은 "화면에 표시될 때까지"입니다.
- 실패 모드를 OOM에 의한 프로세스 전체 종료에서 **오래된 결과 1건의 404**로 바꾸는 것이 목표였습니다. D는 이 목표를 외부 구성요소 없이 달성합니다.
- 바이트 상한은 결과와 컷아웃이 **합산**해서 씁니다. 둘이 같은 프로세스 메모리를 두고 경쟁하기 때문입니다.
- 만료 판정은 `time.monotonic()` 기준입니다. 시스템 시계 변경의 영향을 받지 않고, 테스트에서는 시계 함수를 주입해 시간을 제어할 수 있습니다.

### 기본값 근거

| 설정 | 값 | 근거 |
|---|---|---|
| `IMAGE_STORE_MAX_BYTES` | 64 MiB | 384 MiB 한도를 나눠 본 예산입니다. 프로세스 기본 RSS는 이번 측정(Windows)에서 약 81 MiB입니다. 요청 처리 중에는 업로드(최대 15 MB × 7장), OpenAI base64 응답과 디코딩 사본, 원본 해상도로 리사이즈할 때 PIL이 쓰는 비압축 버퍼가 순간적으로 필요합니다. 이 여유를 남기고 `MemoryHigh=300M` 아래에 머물도록 64 MiB로 잡았습니다. 결과 2 MiB 기준으로 약 30장입니다. |
| `IMAGE_STORE_MAX_ITEMS` | 100 | 아주 작은 이미지가 대량으로 쌓일 때를 막는 보조 상한입니다. 실제로는 바이트 상한이 먼저 걸립니다. |
| `IMAGE_STORE_TTL_SECONDS` | 1800 | 결과 응답 직후 조회하는 흐름에 충분히 긴 값입니다. `Cache-Control: no-store` 때문에 화면이 다시 그려지면 이미지를 다시 요청할 수 있어서 여유를 두었습니다. |

이 값들은 **처리 중 일시 메모리를 실측하지 않은 추정**에 기반합니다. 실제 OpenAI 응답과 큰 원본 이미지로 측정한 값이 아닙니다. 운영 로그의 `store` 필드와 cgroup 메모리를 보고 조정해야 합니다.

### 얻은 것과 포기한 것

- 얻은 것: 저장 데이터의 상한, 요청 수와 무관하게 평평한 메모리 곡선(측정치는 `performance-analysis.md`), 저장소 상태 관측, 저장 실패의 명시적 처리(507)
- 포기한 것: 30분이 지났거나 64 MiB를 넘겨 밀려난 결과는 다시 볼 수 없습니다. 재시작하면 사라집니다. `--workers 2` 이상으로 늘리면 결과를 만든 worker와 조회를 받은 worker가 달라 404가 날 수 있습니다.

### 외부 저장소가 필요해지는 조건

1. worker나 인스턴스를 2개 이상으로 늘릴 때 (스티키 세션 없이)
2. "내 결과 다시 보기"처럼 결과를 세션 밖에서 보관해야 할 때
3. 동시 사용자가 늘어 64 MiB가 표시 중인 결과조차 담지 못할 때 (`evicted`가 늘고 결과 조회 404가 관측되는 경우)

이때는 G(객체 저장소와 짧은 수명의 서명 URL)를 우선 검토합니다.

## ADR-2. 관측 로그 출력 경로 수정

**상태:** 채택 (2026-10-26)

- 문제: `configure_observability()`는 로거 레벨만 설정하고 핸들러를 붙이지 않았습니다. uvicorn은 자기 로거(`uvicorn.*`)만 설정합니다. 그래서 `try_on_me.observability`의 INFO 이벤트가 Python 기본 핸들러(WARNING 이상만 출력)로 넘어가 버려졌습니다. 테스트는 pytest `caplog`가 루트 로거에 핸들러를 붙이기 때문에 통과했고, 그래서 문제가 드러나지 않았습니다.
- 발견 경위: 벤치마크를 준비하면서 uvicorn을 직접 띄워 요청을 보냈을 때, uvicorn 접근 로그 외에는 아무것도 출력되지 않았습니다.
- 결정: 로거에 핸들러가 없을 때만 stdout `StreamHandler`를 붙입니다. 레벨이 꺼져 있으면 `_format_event` 문자열을 만들기 전에 반환합니다.
- 검증: 핸들러 존재를 확인하는 테스트를 추가했습니다. 로그 출력 비용은 벤치마크의 `after`(INFO)와 `after-log-warning`(WARNING) 비교로 따로 측정했습니다.
- 남은 일: 지금은 사람이 읽기 위한 여러 줄 텍스트 형식입니다. 구조화된 필드(`record.event_data`)는 레코드에 그대로 남아 있습니다. 그래서 나중에 JSON formatter 하나만 추가하면 수집 시스템으로 옮길 수 있습니다.

## ADR-3. 벤치마크 방식: 실제 앱 + 고정 크기 가짜 Provider

- 기존 `MockImageGenerationProvider`는 업로드한 인물 사진 객체를 그대로 돌려줍니다. 그래서 저장되는 바이트가 업로드 크기에 묶이고, 실제 OpenAI 결과(새로 디코딩된 1.6~2.0 MB PNG)를 재현하지 못합니다.
- 벤치마크 전용 서버 래퍼(`benchmarks/bench_server.py`)가 측정 대상 버전의 앱을 그대로 불러오고, Provider만 고정 크기의 새 버퍼를 돌려주는 가짜로 바꿉니다. 같은 래퍼로 변경 전 코드(`git archive 119bfff backend`로 추출)와 변경 후 코드를 같은 작업으로 측정합니다.
- 운영과 같은 cgroup 384 MiB 한도를 재현하는 Docker 모드도 만들었습니다. 하지만 작업 환경의 Docker Desktop과 Podman이 기동에 실패해서 실행하지 못했습니다. 이 사실은 결과 문서에 그대로 적었습니다.
